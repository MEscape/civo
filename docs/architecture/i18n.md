# Internationalization architecture

## Decision: one root provider, namespace-scoped providers below it

The root layout wraps the whole tree in `I18nProvider` with the app shell's `app` namespace. Any subtree that holds Client Components needing a module's texts wraps itself in `I18nProvider namespaces={[...]}` and receives only those namespaces.

Why not a single provider with every namespace: the client bundle would ship every module's catalog to every page, including the public sites that use none of them.

Why not one provider per module only: `error.tsx` and `not-found.tsx` boundaries are Client Components outside any module and need the shell texts everywhere; the root provider guarantees them.

## Rules of use

- Server Components use `getTranslations` and `getAppFormatters` (`@i18n/server`); nothing is passed to the client.
- A module's Server Component page declares what its client subtree needs: `<I18nProvider namespaces={['website']}>`.
- Pass `locale` to the provider when the caller already knows it (the layout validated it from the URL). Resolving it from request headers would make the subtree dynamic under Cache Components.
- One namespace per module, owned by that module. A namespace never refers to another's keys.

## Formatting

Dates, numbers, money and relative times go through `getAppFormatters` / `useAppFormatters`, which bind the request locale and time zone. Lint enforces it in module presentation code and `src/app`/`src/components`: importing `formatDate` and the other `@lib/utils` formatters, building `new Intl.DateTimeFormat` (and the other `Intl` formatters), and `toLocale*String` are all errors (`eslint/restrictions.mjs`, `eslint/syntax.mjs`).

The one approved exception is `booking/presentation/hooks/use-zoned-format.ts`: booking times are statements about a place, read in the location's time zone rather than the visitor's. It still takes the locale from the request. Any new exception needs a justified `eslint-disable` pair and an entry here.
