# Internationalization architecture

## Decision: one root provider, namespace-scoped providers below it

The root layout wraps the whole tree in `I18nProvider` with the app shell's `app` namespace. Any subtree that holds Client Components needing a module's texts wraps itself in `I18nProvider namespaces={[...]}` and receives only those namespaces.

Why not a single provider with every namespace: the client bundle would ship every module's catalog to every page, including the public sites that use none of them.

Why not one provider per module only: `error.tsx` and `not-found.tsx` boundaries are Client Components outside any module and need the shell texts everywhere; the root provider guarantees them.

## Rules of use

- Server Components use `getTranslations` and `getAppFormatters` (`@i18n/server`); nothing is passed to the client.
- A module's Server Component page declares what its client subtree needs: `<I18nProvider namespaces={['website']}>`.
- Pass `locale` to the provider when the caller already knows it (the layout validated it from the URL). Resolving it from request headers would make the subtree dynamic under Cache Components.
- One namespace per module, owned by that module. A namespace never refers to another's keys.

## What lives in `src/i18n`

- `config.ts`: the single source of locale facts. `I18N_CONFIG` (`locales`, `defaultLocale`, `definitions[locale]` with `direction` and `openGraphLocale`, time zone, cookie), `Locale` (derive it from here, never re-spell `'en' | 'de'`), `parseLocale` (validates an exact code and returns a result), `requireLocale` (route segment or 404), `getDirection` (the root layout's `dir`), `getMessageFallback`, and the locale-aware navigation (`Link`, `redirect`, `useRouter`, …). It also types next-intl: `Locale` and the English catalog are the `AppConfig`, so `getLocale()`, `useLocale()` and translation keys are already narrowed, and the German catalog must `satisfy` the English schema (`TranslationSchema`).
- `formatters/`: `app-formatters.ts` (`createAppFormatters`, isomorphic), `server.ts` (`getAppFormatters`, `server-only`) and `client.ts` (`useAppFormatters`, memoized by locale and time zone). Consumers import `@i18n/server` and `@i18n/client`, never these files.
- `request.ts` (next-intl request config: catalog loading with a production cache and default-locale fallback, error handling), `locales/` (one catalog per locale), `messages/` (the app shell's namespace), `errors.ts` (stable error codes).
- Add a supported locale in `config.ts` (`LOCALES` and its definition), `locales/<locale>.ts` and each module's message files; `npm run i18n:check` and the type-level `satisfies` hold the rest.

## Formatting

Dates, numbers, money and relative times go through `getAppFormatters` / `useAppFormatters`, which bind the request locale and time zone. Lint enforces it in module presentation code and `src/app`/`src/components`: importing `formatDate` and the other `@lib/utils` formatters, building `new Intl.DateTimeFormat` (and the other `Intl` formatters), and `toLocale*String` are all errors (`eslint/config/restrictions.mjs`, `eslint/config/selectors.mjs`).

The one approved exception is `booking/presentation/hooks/use-zoned-format.ts`: booking times are statements about a place, read in the location's time zone rather than the visitor's. It still takes the locale from the request. Any new exception needs a justified `eslint-disable` pair and an entry here.
