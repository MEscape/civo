# Decisions on proposed components

These decisions follow the change filter in the
[`Designer Agent prompt`](../agents/designer-agent.md): solve a concrete civic
task, inspect existing reuse, and require evidence before expanding a contract.
They do not add components, establish live connections or constitute design approval.
The catalog inspected contains 29 registered components; shared UI is not
automatically a builder-placeable catalog entry.

## Decisions

**Accept shared** means add or reuse a cross-component presentation capability,
without adding a catalog component. **Reuse** rejects a duplicate new component.
**Accept direction; implementation pending** identifies a justified gap whose
contract still needs evidence and a versioned implementation. **Defer** means
the evidence or underlying behavior is incomplete.

## Map capabilities that remain separate work

The current implementation has point styles, line/area rendering, saved maps,
viewport requests and a feature-list alternative. Those are reusable seams,
not verification of the entire requested map suite.

- OGC WMS/WFS overlays and layer transport are **not implemented** by this work.
- Time slider/playback is **not implemented**.
- Actual boundary/statistic joins, 40,000-tree windowing and route/elevation
  data remain **Not Verified** until captured and exercised.
- Privacy gating/self-hosted tiles, keyboard operation, focus return, print
  fallback and script/tile failure require tests of the final implementation.
- A heatmap must identify its density/count meaning. It must not blend cm,
  °C and m³/s into an apparently comparable intensity field.

## Booking capabilities that remain separate work

Reuse the existing booking component and module for supported appointments
and resources. Do not create a second booking engine inside a component.

- **Waitlist is not implemented.** A held slot is not a waitlisted request.
- Required requested states that the existing state machine does not support
  need actual transitions, persistence, authorization and tests before seeding.
- Room reservation, event registration, guided tours and equipment loans need
  evidence that current capacity/duration/resource semantics fit each case.
- Confirmation, reminders, cancellation/rescheduling tokens, duplicate
  prevention and saved drafts are implementation behaviors, not static seed copy.
- A fictional service must never imply that a real municipal appointment has
  been made. Demonstration identity and synthetic provenance must remain visible.

## Review boundary

These are evidence-based accept/reuse/defer decisions and explicit gaps.
They are not a complete visual/state review, a source-license review, a
completed component overhaul, or proof of the minimum sitemap. See
[`PROP-EVIDENCE.md`](./PROP-EVIDENCE.md),
[`NOT-VERIFIED.md`](./NOT-VERIFIED.md) and the milestone log for the separately
recorded implementation and verification status.
